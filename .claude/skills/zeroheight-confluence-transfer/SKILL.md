## Objective

Transfer a component's documentation from a Zeroheight markdown export into a Gemini DS Confluence page, restructured against the fixed component documentation template. **Default source method:** the human pastes the raw Zeroheight markdown export directly into a `<pre><code class="language-markdown">` block on the **target Confluence page itself**, alongside the page's pre-uploaded image attachments — the agent fetches that one page once (`getConfluencePage`, contentFormat: html) to get both the export text and the attachment map in a single call. Chat-paste (pasted directly in the conversation, or a local file path, ideally wrapped in a code fence) remains a supported fallback when staging the export on the page isn't practical, but it has a real history of silently dropping inline image markdown for whole sections — see Known Traps. The Zeroheight MCP connector is never used for this workflow; it will not be available. Images are uploaded to the target Confluence page by a human beforehand — the agent never opens or visually inspects an image; it matches source content to images purely by filename (including exact-hash correlation against the export's own image URLs) and reuses the attachment's existing `data-id`. This keeps the transfer token-cheap and repeatable across components, including when running many components in one sitting.

## Optimization Notes (this fork)

Token-optimized fork of the base skill, revised across three passes.

**v1 (analytical):** (1) Steps 6/7's verification runs as deterministic scripts instead of the agent narrating a text diff over the full body; (2) batch runs (Step 8) dispatch each component to its own isolated subagent, so per-component context doesn't accumulate across a 1–5 component batch — the parent chat shows a one-line status per component, with each subagent's full report available on request.

**v2 (measured):** the v1 script-based checks were correct in principle but still paid a real "transcription tax" — the same ~2,000-token assembled body had to be fully retyped by the model 3-4 times as it crossed Write → Read → updateConfluencePage tool boundaries, measured at ~46% of controllable cost on a single-component run (bigger than the fetches or the checks themselves). Fix: publish the assembled body directly from Step 5 into `updateConfluencePage` in the same turn (no draft-to-disk round trip), and run exactly ONE post-publish verification script against ONE read-back save (Step 7) instead of a separate pre-publish check plus a second post-publish check. The same report also found the target page's attachment fetch was needlessly inflated by unrelated pre-uploaded images — see Step 1.7.

**v3 (this file):** the skill spec itself moved off Confluence (an HTML round trip cost ~20K tokens per fetch/edit) into this local `SKILL.md`, which also makes it directly invokable in Claude Code sessions in this repo instead of a plain reference file. Edit here freely; sync to the Confluence mirror only when explicitly requested.

Image handling itself (filename/hash matching, no visual inspection) is unchanged across all revisions — it was never the cost driver.

## Steps

If running this across MANY components in one sitting (a batch): fetch the master template (Step 3) once at the start of the batch, not once per component — reuse the same fetched structure for every component. Dispatch each component to its own fresh subagent (Agent tool) running Steps 0-7 in an isolated context, passing it the target page ID and the already-fetched template content — see Step 8. Everything else in Steps 0-7 still runs per component, inside that subagent.

**STEP 0: Target Resolution**
1. Confirm the target Confluence Page ID (space ADS) was provided. If not, ask: "Which Confluence page should I update?"
2. Fetch the target page once (getConfluencePage, contentFormat: html). Check for a `<pre><code class="language-markdown">` block containing the raw Zeroheight export — this single fetch also serves as Step 1's attachment harvest, so don't fetch the page twice.
3. If no code block is present on the page, fall back to asking the human to paste the export directly in chat (ideally wrapped in a code fence) or provide a local file path. Never attempt to use the zeroheight MCP connector for this — it will not be available for this workflow, regardless of what appears connected in the session.

**STEP 1: Verify pre-uploaded images**
1. From the Step 0 fetch, extract every media node's filename, data-id, and data-collection into a filename -> {data-id, data-collection} map.
2. Try exact-hash correlation FIRST: Zeroheight export image URLs embed the original upload hash (e.g. /uploads/\<hash\>.svg, s3-accelerate.amazonaws.com/\<hash\>?...) — this hash is very often exactly the attachment's filename already on the page, sometimes with an upload timestamp suffix appended (e.g. \<hash\>-20260812-135900.png) — match on the hash prefix before any such suffix, not full-filename equality. Match on that before assuming anything needs renaming.
3. Only if, after hash correlation, an export image reference still has no matching attachment: STOP and ask the user to rename the relevant attachment(s) before continuing. Do not guess a filename's meaning from the image.
4. Ask the user for the total attachment count on the page (Confluence's Attachments panel), or otherwise confirm it. Compare that to the number of export image references successfully matched. When the export came from the page's own code block (the default method), a large fraction of unmatched attachments is normal and NOT a sign of a bad export — it usually just means extra/unrelated attachments with no textual anchor in the export; note them in the Step 7 report rather than escalating. When the export came via the chat-paste fallback instead, a large mismatch (more than a couple) IS a known failure signal — see Known Traps — and should prompt asking the human to re-paste wrapped in a code fence (or better, to stage it as a page code block instead) before concluding the export is genuinely incomplete. Never use a scraped-folder or metadata-file image count as either baseline — such exports typically include Zeroheight navigation/chrome images that were never meant to become attachments, and will produce false positives.
5. (Chat-paste fallback only) Bare sub-headings with no visible caption or "Add notes" text directly under them (e.g. per-size or per-shape variant headings like "Circle" / "Square") are a strong signal that images were silently dropped from that section specifically — flag these to the human and suggest re-pasting in a code fence, or staging the export as a page code block instead, before treating the section as genuinely empty.
6. If a media node has no filename text (blank) or an unusual wrapper, it cannot be identified — leave it unused rather than guessing which export image it corresponds to.
7. Token-cost note, not a correctness rule: a large pool of pre-uploaded attachments unrelated to the export text makes the Step 0 page fetch proportionally larger for no benefit — one measured run fetched ~50 media nodes for only 6 actually referenced. This doesn't block the transfer, but if asked to advise on staging (or before starting a fresh component in a batch), tell the human to keep the target page's attachments limited to images the export actually references.

**STEP 2: Parse the source export into content units**
1. Break the raw export into discrete units: one per heading, paragraph, bullet, platform-status line, resource link, and each image reference (with its adjacent caption, even if it is only a placeholder like "Add notes").
2. Classify links by URL shape and destination, not by guessing: a full https:// URL to Figma or Storybook is a genuine resource link and is a content unit. A relative Zeroheight path (e.g. /626199550/p/...) is the tool's own navigation chrome — discard it, it is not a content unit. A full https://zeroheight.com/... URL that points back into Zeroheight itself (an internal cross-reference, not Figma/Storybook) is ambiguous — STOP and ask the user whether to drop it, keep it as plain text, or keep it as a live link. Do not default to auto-including it just because it has a real https:// scheme.
3. Before treating a repeated image reference as a scraping/extraction bug (e.g. the same image appearing to represent multiple distinct states), checksum the candidate files. If they are byte-identical, the repetition in the export is legitimate content reuse, not an error — do not "fix" it by inventing distinct images.
4. Keep the resulting unit list — it is the checklist for Step 7's verification.

**STEP 3: Read the master template**
1. Read `template.html` from this skill's own folder — do NOT fetch Confluence page 3430449284. The owner (Gabriel Saint Martin) maintains this template directly and will say explicitly when it has changed; only then, fetch the live page (contentFormat: html) and overwrite `template.html` with the fresh copy before continuing. Read once per session/batch, reused across every component processed in the same sitting (see the batch note above).
2. Note section order and exact conventions: platform table placement, panel-note markup for "Not documented", DO/DON'T/CAUTION cell backgrounds (#e3fcef / #ffebe6 / #fff0b3), #f4f5f7 headers for neutral/variant-comparison/related-component tables, and that every image is a figure[data-type="media-single"] wrapping a div[data-type="media"] (never a bare media div — see Known Traps). Confirm exact color values against this local file — do not reuse a value from memory. The template may define additional table patterns beyond the standard 2-column DO/DON'T (e.g. a 3-column DO/DON'T/CAUTION) — always defer to what `template.html` actually shows.

**STEP 4: Map every content unit to a template section**
1. Assign each unit from Step 2 to its matching template section (Platform table, Usage, Platform [H3 under Usage, optional], When to use / NOT to use, Variant Selection Flow, Usage Guidance DO/DON'T, Variants & Modifiers per category/variant, Related Components, Behavior & Responsiveness, Content & UX Writing, Accessibility).
2. Genuine resource links (Figma, Storybook) belong in or directly beneath the platform availability table — this is a defined placement, not an ambiguous unit; do not escalate it.
3. Any platform-specific narrative (custom vs. native design, Web/iOS/Android behavioral differences, "All platforms (custom)" / "iOS and Android (native)" style breakdowns) maps to the "Platform" H3, the FIRST subsection under "Usage" — right after the one-line narrative, before "When to use". This section is optional: omit it entirely (no heading, no "Not documented" placeholder) when the source has no platform-specific narrative beyond the readiness table. Never place it as a standalone H3 floating above the page's first divider — that was a real bug (see Known Traps) that left it orphaned outside any template-mapped section, with inconsistent heading levels between components.
4. For a comparison pair or set that is not DO/DON'T (e.g. "With border / Without border", "Web / iOS-Android", named states like "Expanding / Collapsing"), use a table with one column per named variant, #f4f5f7 headers, and one image per cell — this is the standard pattern for non-DO/DON'T side-by-side comparisons.
5. If a unit still fits no section, STOP and ask the user where it belongs. Never invent a new section, never drop it, never dump it into a generic catch-all.
6. For every template section with zero mapped units, still include the heading, followed by: `<div data-type="panel-note"><p>Not documented</p></div>`. Never omit a section. (Exception: the optional "Platform" H3 from point 3 — omit entirely, don't panel-note it.)

**STEP 5: Assemble the page body**
1. Do not add the component name as an H1 in the body — the page title already carries it.
2. If the export includes a hero/preview image near the top (typically directly under the component name/description, before any Do/Don't or variant content), place it immediately after the one-line summary and before the platform table — preserve the export's own top-of-page position.
3. For every image unit, insert its wrapped media reference using the data-id/data-collection harvested in Step 1. Never invent an ID.
4. If a filename correlates correctly to an export image but its data-id turns out unresolvable when read back (e.g. UNKNOWN_MEDIA_ID), publish the surrounding text without that image — do not block the whole transfer over one broken attachment — but it MUST be named explicitly in the Step 7 report, not folded silently into a general note.
5. If the human re-uploads previously-missing images by dragging them into the page body (rather than the Attachments manager), Confluence appends them as a trailing block of standalone media figures with visible filenames — this is the expected way to harvest their data-id for Step 1. That trailing block must be fully removed from the final assembled body; it is a temporary staging artifact, not final content.
6. Likewise, when the export was sourced from a `<pre><code>` block staged on the target page (the default method), that code block is ALSO a temporary staging artifact — it must be fully removed from the final assembled body, exactly like the trailing media dump in point 5. Never leave the raw markdown visible as a live code block on the published page.
7. Do not include any QA/verification/check table in the body. That information is internal only.
8. DO/DON'T pairing rule: a DO/DON'T table row always holds a matched pair describing the same rule from both sides. Never add a row with an empty or placeholder ("—") cell just to keep an unpaired item in the shared table — that renders as visibly broken. If a DO (or DON'T) has no genuine opposite, pull it into its own single-column table (colored DO-green or DON'T-red, matching the item's polarity); group multiple unpaired items of the SAME polarity together in that one table (one row each) rather than one table per item. The same rule extends to a standalone CAUTION with no matching DO/DON'T — give it its own single-column amber (#fff0b3) table rather than squeezing it into a shared row.
9. Wide variant-comparison tables (one column per named size/shape/variant): cap at 5 columns. Confluence's storage API can silently split a wider table mid-write, and the split-off portion loses its header styling — always re-fetch and inspect after publishing to catch this. If a variant set has more than 5 members, split it into multiple evenly-sized tables yourself (e.g. 5 + 5) with matching header colors on every part, rather than risking an invisible, unstyled split.

**STEP 6: Publish (no draft-to-disk round trip)**
1. Pass the assembled body from Step 5 directly as the `body` argument to `updateConfluencePage` (contentFormat: html) in the same turn it was assembled. Do NOT write it to a scratch file and read it back first just to re-paste it into this call — that round trip forces the model to fully retype the entire body twice for zero benefit; it was measured as the single largest avoidable cost on a real run. Never pass shell heredoc syntax as the body value.
2. There is no separate pre-publish verification pass — Step 7 below is the only verification, and it runs after this publish, against the real published result.

**STEP 7: Verify after publishing (mandatory — ONE script pass against ONE read-back)**
1. Read the page back (contentFormat: html) exactly once and save it to a scratch file exactly once — do not reason over the fetched body inline, and do not save a second copy for a separate check. This single file is checked by the single script in point 2 below.
2. Run one python3 script against that file that: (a) for every unit from Step 2, confirms its normalized text (text units) or filename (image units) is present via a real string-containment check; (b) confirms the raw Step 0 code-block text does NOT appear verbatim anywhere in the body (it must have been replaced by structured content, not left alongside it); (c) greps for `__confluenceADFMigrationUnsupportedContentInternalExtension__` (a leaked unsupported-media placeholder); (d) counts columns in every table to flag any table whose column count doesn't match what was written (a silent split, per Step 5.9); (e) flags any DO/DON'T/CAUTION table row containing an empty or dash placeholder cell (an unpaired row that leaked through, per Step 5.8). Have the script print ONLY the flagged issues — never the full page or full unit list back into context.
3. If anything is flagged, fix the assembly, re-publish (Step 6), and re-run this same script against the fresh read-back — never trust a stale copy, and never re-derive the check yourself by reading the full body. Do not consider the transfer done with a known gap.
4. Do not trust the page's own version-history "summary" field as a proxy for what the body contains — it can describe edits that don't match the actual body; this script checking the real fetched body is the only source of truth.
5. Report to the user in chat only (never on the page): which export source was used (page code block default, or chat-paste fallback), units mapped, sections marked "Not documented", images embedded, any broken media ID named explicitly, any attachment-count mismatch found (and whether it was expected/reported vs. escalated), and confirmation the Step 7 verification script passed clean (or what was flagged and fixed).

**STEP 8 (batch runs only): Isolate each component and move to the next**
1. Run Steps 0-7 for one component inside its own fresh subagent (a new Agent tool call, not a continuation of the parent's conversation) — pass it only the target page ID and the Step 3 template content already fetched by the parent; nothing else from prior components' work. The subagent still returns its full Step 7.5 report as a structured result.
2. In the parent chat, print only a one-line status per component as each subagent finishes (e.g. "Accordion done — moving to Badge (2/3)"), not the full report — but keep each subagent's full structured report available to surface in full if the user asks for detail on a specific component.
3. Move to the next component's markdown/page pair and repeat, passing the same already-fetched Step 3 template content into each new subagent rather than having every subagent re-fetch it.
4. If a subagent hits a STOP-and-ask checkpoint (Steps 1-4), it pauses and surfaces that question to the parent immediately rather than guessing — the parent relays it to the user before continuing that component.

## Known Traps & Resolutions

| Trap / Behavior | Root Cause & Resolution |
|---|---|
| **Retyping the same body across tool boundaries is the biggest avoidable token cost, not the verification logic** | A measured single-component run showed ~46% of controllable cost came from the model fully retyping the same ~2,000-token assembled HTML body 3-4 times: once into a draft `Write`, again via `Read` just to get it back into context before publishing, again as the `updateConfluencePage` argument, and a fourth time saving the post-publish read-back for a second check. Switching the verification logic itself from narrated reasoning to a script (the v1 fix) did NOT remove this cost, because the round trip through disk was still happening. **Fix:** publish directly from the assembled body in the same turn (Step 6), and read/save the post-publish body exactly once for exactly one verification script (Step 7) — see Optimization Notes. |
| **A large pool of unrelated pre-uploaded attachments inflates the Step 0 fetch for no benefit** | One measured run staged an export whose target page carried roughly 50 media attachments, of which only 6 were actually referenced by the export text — the other ~44 still had to be parsed out of the Step 0/1 fetch every time. This is not a correctness problem (Step 1.4 already treats it as an expected, reportable mismatch, not an error) but it is a real, avoidable cost. **Fix:** when advising on staging, or between components in a batch, tell the human to keep the target page's attachments limited to images the export text actually references (see Step 1.7). |
| **The skill spec itself is expensive to iterate on if kept only on Confluence** | Every `getConfluencePage`/`updateConfluencePage` round trip against the skill's own instructions page costs roughly 20K tokens (full HTML body, entity-escaped, with `data-local-id`s on every element). Iterating on the skill spec by fetching/editing/republishing Confluence directly on every change compounds that cost per edit. **Fix:** this `SKILL.md` is the working copy and the invokable skill at once; edit it directly with Read/Edit. Sync the Confluence mirror only when the user explicitly asks — never fetch/update it as part of normal iteration on the skill's own instructions. |
| **The master template was also being re-fetched from Confluence on every session for no reason** | Step 3 used to fetch the live Confluence template page every session/batch — a recurring cost for a page that changes rarely. Unlike a component's own doc (which genuinely differs every run), the template is a fixed reference the skill owner controls directly. **Fix:** cached verbatim as `template.html` in this skill's folder (see Prerequisites). Use it by default; only re-fetch and overwrite it when the owner explicitly says the template changed — do not re-fetch speculatively or on a schedule, since staleness protection here relies on the owner being the only editor, not on the skill re-checking. |
| **Chat-paste export fidelity is unreliable — now avoided by default** | A plain chat paste, a bulk export-tool file, and even a saved `.md` file read from disk have all reproduced the same failure: entire image blocks (an icon/illustration comparison, a per-size variant grid, a whole modifier section) silently dropped from the export while surrounding headings and text stayed intact — apparently because the client used to view/copy the Zeroheight page renders inline images and drops the underlying markdown syntax on copy. **Resolved by default:** have the human stage the raw export in a `<pre><code class="language-markdown">` block directly on the target Confluence page instead of pasting in chat — reading it back via `getConfluencePage` returns the literal text untouched, since Confluence's storage format doesn't re-render code blocks. Confirmed reliable with zero re-asks needed on the one component sourced this way from the start, versus a required second attempt on two components sourced via chat-paste. If chat-paste must be used as a fallback, wrapping the paste in a code fence first partially mitigates the issue but is not as reliable as page-staging — treat a large image mismatch on that path as a real signal (Step 1.4) rather than assuming completeness. |
| **Attachment filenames from page-staged uploads can carry an appended upload timestamp** | When images are uploaded directly to the target page (the default method's staging area), Confluence sometimes appends an upload timestamp to the filename, e.g. `<hash>-20260812-135900.png`, where `<hash>` still matches the export's own image URL hash exactly. Match on the hash prefix before any such suffix — do not require full-filename equality, and do not treat the suffix as evidence the file needs renaming. |
| **A standalone CAUTION with no matching DO/DON'T renders as visibly broken if squeezed into a shared table** | Same failure mode as the unpaired-DO/DON'T trap below, but for a lone CAUTION with no paired DO or DON'T in the source (observed on Carousel's Arrow position and Dots sections, each with a standalone Caution and its own image). Fix: give it its own single-column table with the amber #fff0b3 header, exactly like an unpaired DO or DON'T gets its own single-column green/red table — never force it into a shared row with an empty cell. |
| **"Platform" narrative left as an orphan heading above the first divider** | Platform-specific narrative (custom vs. native design, Web/iOS/Android behavioral differences) isn't a Figma/Storybook-link-style unit and has no obvious template slot, so it was placed inconsistently across components: a standalone H3+H4 block sitting above the page's very first `<hr>` on some pages, folded into a plain paragraph with no heading at all on others, and simply dropped on components with no such content. The visible symptom looked like a "missing divider," but the real cause was an unmapped section, not a divider bug. **Fix:** the template now defines "Platform" as an optional H3, the first subsection under "Usage" — see Step 4.3. It inherits the divider that already precedes "Usage" and needs no divider of its own. |
| **An unpaired DO or DON'T squeezed into the shared table (as an extra row with an empty/dash cell, or as a bare unstyled paragraph) renders as visibly broken** | Happened twice: once as a second table row with a literal "—" placeholder in the opposite column (Alert's Usage Guidance, Autocomplete's Dropdown list), and once as three plain `<p><strong>DO:</strong>...</p>` blocks with no table/color at all (Alert's Platform section) — both read as inconsistent or broken next to the properly-styled DO/DON'T tables elsewhere on the same page. **Fix:** an unpaired DO or DON'T never shares a table with a paired row — it always gets its own single-column, single-polarity table (see Step 5.8 and the template's example). |
| **Wide variant-comparison tables can be silently split by Confluence, and the split-off part loses its header styling** | A 10-column size-variant table (Avatar's "Square" grid) was split by Confluence's storage API into two separate tables mid-write — one 6-column, one 4-column — and the second table lost its `#f4f5f7` header background entirely. An identical 10-column table elsewhere on the same page ("Circle") was NOT split, so the trigger isn't a fixed column count — treat any table beyond ~5 columns as at risk. **Fix:** cap variant tables at 5 columns; split larger sets into multiple evenly-sized, matching-styled tables yourself (Step 5.9), and always re-fetch after publishing to confirm no table was split unexpectedly. |
| **Bare media div renders as an unsupported extension** | Confluence's storage format requires `<div data-type="media">` to be wrapped in `<div data-type="media-group">` or `<figure data-type="media-single">`. Without the wrapper, the API silently accepts the write but renders it as `__confluenceADFMigrationUnsupportedContentInternalExtension__` instead of an image. Always wrap. |
| **Page title rename fails: "A page with this title already exists"** | Title uniqueness is enforced per space. Don't try to rename an existing page to match a component name if that title is taken elsewhere in the space — set the title once, at page creation, and leave it. |
| **Tiny `/wiki/x/...` links don't resolve via the Confluence MCP tools** | Despite the tool description claiming tiny-link support, passing the short code as `pageId` fails with a type error, and following the redirect via WebFetch just hits Confluence's login wall. Always get the numeric page ID (Page Information, or the resolved URL) instead. |
| **`cloudId` as the bare hostname returns malformed or cached-looking results** | Use the UUID cloud ID from `getAccessibleAtlassianResources`, not `avivgroup.atlassian.net`. |
| **Shell heredoc syntax breaks the page body** | Passing `<<'HTML' ... HTML` as a tool's `body` parameter is not a shell invocation — the markers become literal page content and can wipe out every media reference on the page. Never use shell syntax inside a string parameter. |
| **Zeroheight image "captions" are often just the placeholder text "Add notes"** | This is not real content — don't treat it as a caption to preserve verbatim as meaningful text, and never invent a real caption to replace it. |
| **No MCP tool uploads Confluence attachments** | Image upload is a human step that happens before the skill runs, for every component — batching does not remove this, it only front-loads it. The skill must not attempt to upload images itself or shell out to `curl` with credentials to hit the REST attachment endpoint. |
| **Zeroheight MCP connector is never used, by design** | This is a deliberate, permanent process decision — not a workaround for a temporary outage. The export is sourced from a page-staged code block by default, or shared directly by a human as a fallback, and the connector will never be available for this workflow. Never attempt to use it, even if it appears connected in the session. |
| **Attachment filenames don't need renaming as often as expected** | Zeroheight export image URLs embed the original upload hash, and that hash is frequently the attachment's filename as-is on the Confluence page (occasionally with a timestamp suffix — see the dedicated trap above). Try exact-hash string matching before treating a filename as unresolvable and escalating a rename request — don't cry wolf on a well-formed export. |
| **Confluence's own version-history "summary" field is unreliable** | It can describe edits (e.g. "Added Related components block") that don't match what the page body actually contains when fetched. Never use it as a proxy for "has this already been transferred" — always read the real body. |
| **Scraped-folder/metadata-file image totals overcount real content** | A whole-page scraper captures Zeroheight's own navigation, footer, and logo images alongside real content images. Comparing against that total for the Step 1.4 mismatch check produces false positives — always anchor the check to real Confluence attachments and real markdown image references, never to a scraped-folder or metadata-file count. |
| **Table header colors are exact values, not approximate** | Neutral/grey headers are `#f4f5f7`, not `#f5f5f5` — a one-character difference that's easy to misremember. CAUTION is `#fff0b3` (amber), not grey — it needs to visually read as a warning, distinct from a neutral variant-comparison header. Always confirm exact values against the freshly-fetched template rather than reusing a memorized value. |
| **Batching many components does not mean unattended automation** | The Step 1-4 STOP-and-ask checkpoints (hash mismatch on the chat-paste fallback, unmapped content, broken media ID, ambiguous internal links, blank-filename attachments) still fire per component in a batch. Batching front-loads image uploads and avoids re-fetching the template per component, but it does not remove the need for per-component human review at each checkpoint — do not present a batch run as "fully automated." |
