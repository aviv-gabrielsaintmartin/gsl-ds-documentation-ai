# Known Traps & Resolutions — figma-sync-component-sets

Covers all three tiers (`components`, `patterns`, `experiences`) — this skill was generalized from a Components-only version on 2026-08-26; the traps below carried over unchanged since they're Figma Plugin API behavior, not tier-specific.

| Trap / Behavior | Root Cause & Resolution |
|---|---|
| **False Deletion / Stale Node Cache** | Single-pass bridge queries can miss variant nodes if pages aren't fully loaded in memory. Never mark a variant/option/property "removed" without first running `await figma.loadAllPagesAsync()` and re-querying the component set at least twice. |
| **Property ID Suffixes (`#id`)** | Raw `componentPropertyDefinitions` keys look like `Name#123:0`. Strip the suffix for display titles, but keep the exact payload reference when writing code/API specs. |
| **Preserving String Typos** | Typos in Figma names (e.g. "Checkbox goup", "Standelone") must be preserved in property tables so programmatic payloads match live Figma layers. |
| **Pattern Classification** | A component/pattern/experience is Pattern 2 only if nested sub-components have `isExposedInstance: true`. Internal layers (`isExposedInstance: false`) stay Pattern 1. |
| **Overwriting Manual Notes** | When updating a registry entry, preserve any manually-added notes/usage guidance already present rather than overwriting wholesale. |
| **Text Property Omission** | Some components (e.g. Button) lack a formal `TEXT` property. Label overrides target internal TEXT nodes directly — document this under the component's own notes. |
| **Silent Bridge Disconnection** | The Desktop Bridge disconnects whenever the Figma file is edited. Re-run the plugin and verify via `figma_get_status` (`probe: true`). |
| **Public pattern built from private dot-prefixed helper sets on the same page** | Confirmed live in the Patterns library (2026-08-26): a page like "Burger menu" holds a public `Burger menu` `COMPONENT_SET` plus private `.base_burger menu` and `.base_profil` helper sets used to build it. Register only the public set; leave `.`-prefixed sets unregistered, same convention already used in Components (`.Select card AI test`). |
| **WIP / in-progress pages read as real components** | A page name prefixed `(WIP)` or containing "Refacto" (seen on Components' "Tabs" page, where a `Tab Bar` set lives inside a "Refacto" section) signals an unfinished component. Flag it and ask before registering rather than treating it as a finished, documentable entry. |
| **A component nested inside a "Documentation ..." frame is NOT a staleness signal** | Confirmed by the design owner (2026-08-26, Patterns library): some real `COMPONENT_SET`s are deliberately placed inside a frame named "Documentation \<thing\>" purely for presentation/review layout on the page — this is a permanent, intentional convention in this library, not evidence of an orphaned duplicate or an unused draft. Don't treat page-root placement as a signal of "realness" either — `Burger menu` (nested in a Documentation frame) and `Burger menu (profil)` (page root) are both equally real, separate components with different keys. Do flag TWO components sharing identical variant/prop shape but different keys as worth a human confirmation before registering both — that ambiguity is real and was worth asking about — but don't default to assuming the nested one is the duplicate. |
| **A leading `(❌ OUTDATED)` or similar marker in a component's own name means deliberately deprecated** | Seen in Experiences library, "Map experience" page: `(❌ OUTDATED) mapPins` sits alongside `mapPinsV2_SL` / `mapPinsV2_IWT`. Treat the marked one as excluded from the registry (don't register it, note it in `audit-log.md` as superseded), and register its un-marked successor(s) instead. Unlike the WIP/Refacto trap (unfinished, not yet real) this is the opposite lifecycle stage (finished, but retired) — same STOP-and-don't-silently-register response either way. |
| **A `.`-prefixed PAGE name doesn't itself hide the components on it — only a dot on the component's own name does** | Seen in Experiences library: page `.Listings` held sets named `listing_tags_list`, `listing_price_tag`, etc. with no dot on the component names themselves. Flagged as ambiguous, then resolved same day: the design owner explicitly renamed all 7 with a `.` prefix live in Figma. There is no separate Figma "hidden from publishing" API flag for components (unlike variables/styles — see `architecture.md`); the `.`-prefix naming convention IS the actual mechanism here. Don't infer privacy from the page name alone — check each component's own name, and ask if it's ambiguous. |
| **When checking whether a private helper is genuinely in use, match by `mainComponent` key, not by the exposed instance's display name** | Instances of a private helper get renamed on use (e.g. `.listing_tags_list` shows as "Tags list" inside `Listing Card`, `.listing_price_tag` as "Price tag"). Walk exposed instances, call `getMainComponentAsync()` on each, and compare `key` — never assume an instance is unused just because no exposed instance shares its literal name. |
| **A parent's own `componentPropertyDefinitions` does NOT include its exposed nested instances' properties** | Figma doesn't merge them up. To set an exposed slot (e.g. `Listing Card`'s "Property features") an agent must locate that nested instance node (by name, within the parent instance's tree) and call `setProperties()` on THAT node, using the private component's own definitions — not on the parent instance. This is why Pattern 2 registry entries carry a structured `exposedSubComponents` array (exposedAs / key / name / properties) instead of just a Pattern-2 label — an agent needs the reachable slot name and its valid property values, not just confirmation that composition happened. |
| **Query a different connected library file without switching the active Figma window** | `figma_execute` accepts a top-level `fileKey` argument (not a `figma.getNodeByIdAsync` option) that targets any file the Desktop Bridge plugin is already connected to, independent of which one is currently focused/active in Figma Desktop. Used to backfill Patterns/Experiences/Components data in the same session without asking the owner to switch tabs each time — only works for files where the plugin is already open and connected (`figma_get_status` lists `connectedFiles`). |
| **A registered component's real live name doesn't always match the display name used elsewhere (registry, Confluence, master index)** | Confirmed while backfilling: `Checkbox Group`'s real name is `Checkbox goup` (typo, matches an existing trap), `Navigation Bar (App)`'s real component is named `Navigation Bar` (the "(App)" suffix is the page name, not the component name), `Select Card Group`'s real component is named `Select card`. All matched correctly by `key`, confirming the registry's existing keys were right — search by exact name first, but fall back to a broader contains/fuzzy search across the file if an exact match comes up empty before concluding a component doesn't exist. |
| **A "component family" can be several standalone COMPONENTs with no shared COMPONENT_SET at all** | First seen in Foundations' `Brand App Icons` (2026-08-27): 31 unrelated standalone `COMPONENT` nodes (per-platform/per-brand app icon exports), no variant properties, no parent set to register. Don't force these into the variant/pattern schema — register the family as one entry with an `assets: [{name, key, nodeId}]` array instead of `variantCount`/`pattern`. |
| **A component composed internally from a private dot-prefixed helper set can still be Pattern 1** | `Brand Logo` and `Favicon` (Foundations, 2026-08-27) are each built on a private helper (`.Logo`, `.Brand Favicon`) but an `isExposedInstance` walk found zero exposed nested instances on either — the helper's variants are baked in per top-level variant, not exposed for external configuration. Composition-from-a-private-set is not itself evidence of Pattern 2; always run the live walk. |
| **A library's multibranding mechanism can live one level below the parent's own variant, not on it** | Foundations' 173 illustrations (2026-08-28) each expose only one property, `Size` — but 172/173 also compose exactly one exposed instance ("Variable tag" → private `.Alerts - Tag` set) whose *own* variant carries `Style` (`Accent`/`Isometric`/`Matilde`/`None`), the actual per-brand rendering switch. This is the standard Pattern 2 `exposedSubComponents` shape, just unusually uniform (same single slot name/set across the entire catalog) — don't mistake a parent's narrow `componentPropertyDefinitions` (just `Size`) for the full configuration surface; always capture the exposed slot's own properties too, same as any other Pattern 2 component. |
| **Perfect uniformity across a large catalog is a signal to verify the outlier, not to skip checking it** | All 173 Foundations illustrations share the identical `Size` options and 172 share the identical exposed-slot shape — except one (`Info Reset Password Email`, zero exposed instances) and the `HP` category (no `COMPONENT_SET`s at all, just 2 standalone `HeroIllus` COMPONENTs). A 99%+ uniform pattern makes the exceptions easy to miss in a spot-check; a full sweep across every entry (not a sample) is what surfaced both — worth the extra query cost on a catalog this size. |
| **`figma.getNodeById` fails through `run` with a transport-shaped error that blames the connection** | Seen 2026-09-16. A script using the deprecated synchronous `figma.getNodeById` returns `✗ Not connected to Figma` plus the `connect` / `connect --safe` advice — which reads as a dead daemon or a detached plugin, and sends you to restart things that are fine. The daemon and the plugin were both healthy; `status` and an `eval` round-trip both passed immediately after. **Use `await figma.getNodeByIdAsync(id)`** in anything run under `documentAccess: dynamic-page`. More generally: when `run` reports a connection error, re-test with `eval` before asking Gabriel to restart the plugin — an `eval` that answers proves the error came from your script, not the channel. |
| **A stored `pattern` value on an entry with no `nodeId` predates the Gemini → GSL library migration and must be re-verified, never trusted** | `Cell Content` carried `"pattern": "Pattern 1"` with a status line asserting that a live `isExposedInstance` trace had found nothing nested. A walk on 2026-09-16 found one exposed slot on all 33 variants. **Gabriel confirmed the old entry was simply wrong, not out of date** — the slot had not been newly exposed, so a status line asserting a live trace is not itself evidence one was run correctly. The entry had no `nodeId` and no `auditedDate`, which is the tell: those entries came from the Confluence backfill or from the retired Gemini file, whose node IDs no longer resolve. **Treat a missing `nodeId`/`auditedDate` pair as "unverified against the current file", whatever the `pattern` field says**, and re-run the walk before reusing the classification. The reverse of the existing composition-is-not-exposure trap: a stale Pattern 1 is as wrong as a hasty Pattern 2. |
